# Probe 4.1.15.35 / 270115 静态适配证据

本档和 [`hook/experimental/4_1_15_35_mac.json`](../hook/experimental/4_1_15_35_mac.json) 是实验性地址记录，**尚未完成稳定收发验证**。它不在 `hook/versions/` 支持列表内，不能直接交给上游完整 hook 渲染器。未知地址保留 `null`，发送和 closure capture 均关闭；不能用 270135 地址填空。

固定目标为 arm64，UUID `9CEB6CCF-81A5-3B7F-8FB5-B4256FE67EEB`，arm64 slice SHA-256 `6d3feb56043cb63d2ff3f77aa32115abbfe7a2f28b3ab1ab59886ee625703e4b`。表中均为未滑动的模块虚拟地址；磁盘 vtable 使用 chained fixup 编码，原始八字节不能直接当运行指针。

## 当前候选

| 对象 | 地址 | 静态依据 |
|---|---:|---|
| Message finalizer | `0x4b573b8` | 固定前缀唯一命中；构造器以 mode 1 调用；不是每次调用都代表新消息 |
| Message vtable | `0x9cdb068` | 构造器 `0x4b5611c` 明确写入对象首地址 |
| std::string 构造 / scope 查找 | `0x57bbb74` / `0x57bb528` | `MMStartTask` wrapper 构造 `default` 并调用 scope registry |
| `default` 字符串 / operator new | `0x967810d` / `0x6fc04a8` | 真实调用链、导入符号及字符串字节 |
| service holder | `0xa27a168` | 初始化函数存入 holder；其 vtable+0x18 getter 返回 holder+0x250 的 service |
| classA vtable / slot13 | `0x9cba4e0` / `0x44d33a8` | 构造器写入 vptr；slot13 注册 native task，维护 root+0x70/count+0x78 |
| 文本 task 构造 / vtable | `0x2f8888c` / `0x9c12fb8` | 原生文本 factory 分配0xe0，调用该 ctor；初始化 B1+0x78/B2+0xa8 |
| 文本 closure vtable / clone | `0x9c13010` / `0x2f88c64` | 原生文本 caller 分配0x30 closure；clone 复制 capture 并增加共享引用计数 |

接收 Message 的静态字段包括 type+0x0c、from+0x18、to+0x30、senderName+0x48、serverId+0xf8、秒时间+0x114、content+0x130、msgSource+0x160、扩展对象+0x220、finalized flag+0x258。字符串为24字节 libc++ 布局。字段业务语义、方向、重复处理和长短 UTF-8 仍需独立测试账号的已知消息验证。

发送链从实际指令恢复，没有平移旧版本偏移：

1. 描述 builder `0x2f86f24` 从常量片段拼出 `/cgi-bin/micromsg-bin/newsendmsg`，设置 opcode0x20a、URL+0x18 和 flags。直接 `strings` 搜不到这段完整 URL。
2. factory `0x2f886c4` 调用 builder、分配0xe0、调用 task ctor；ctor 把 opcode 写到 task+0xc、初始化 serializer，并清空 closure+0x68。
3. caller `0x2f88404` 构造真实 closure；factory 将其转移到 task+0x68，再调 service vtable+0x28。
4. service thunk `0x44d4074` 是 `sub x0,x0,#0x10; b 0x44d33a8`。slot13 通过 `MMStartTask` 注册任务，保存 task ID 和 tree node。

## 复验

只读取明确提供的磁盘模块，不会发现、启动、attach 或停止任何进程：

```sh
python3 tools/probe_static.py --module /absolute/path/to/WeChat-Main-Probe.app/Contents/Resources/wechat.dylib
```

脚本复用 `probe_target.inspect_module()` 校验固定 UUID/hash，补充磁盘 segment 地址映射和接收、descriptor、task、closure、service 的指令/vtable 锚点。通过时输出 `static_anchors_verified`，同时始终保留 `runtime_verified:false`、`enableSend:false`。这只证明所提供磁盘文件符合记录，不证明任何运行进程绑定或账号状态。

2026-11-15，在固定测试 Probe 上完成 metadata 附加及退出、180 秒接收观察及退出，原 owner 代次与独立 postflight 均通过。接收观察记录 0 条匹配测试前缀的样本，不能据此确认消息读取正确。

## 原有 closure 观察路线（供对照）

必须先通过独立 Probe 的显式 PID、路径、启动时间、模块身份及现有 debugger owner 门槛。动态观察器只在获准的 Probe 上短时运行，退出时只卸载自己安装的观察器。

- 在 `slot13` onEnter 中只检查 x1 指向的 task：可读且长度至少0xe0、vptr等于本模块 task vtable、opcode+0xc等于0x20a。
- 读取 task+0x68 的 closure 指针；确认至少0x30可读、vptr等于本模块 closure vtable、vtable+0x10指向预期 clone。记录匹配结果和模块相对类型地址即可；不要读取正文、联系人或 closure capture 内容。
- 仅观察一条由用户在测试对话中手动发出的文本，然后卸载。先验证该文本实际送达、Probe 登录态正常。只看到一个匹配 closure 只能证明当时存在该类型对象。
- 此阶段不调用 clone、ctor、NativeFunction、slot13 或任何原生 API，不保存/跨重启复用 heap 指针，不启用自动发送。继续发送测试前还需确认 clone 的所有权、线程和生命周期，之后才做单条有唯一标记的测试及接收方送达验证。

一次 `slot13` 返回值或匹配 vptr 不能证明自动回复稳定。接收去重、自发消息过滤、重新登录、进程重启后 seed 失效、超时与长时间运行均属于后续验收。
